# AI 小镇设计方案

## 1. 目标

将 `OpenClaw + ClawPanel` 扩展为一个本地可运行的轻量网页游戏模式。

用户进入页面后，不是先看到传统后台，而是先进入一个 2D 俯视角像素小镇：

- `OpenClaw` 是老板角色，负责带队、管理、分配工作
- `Agent` 是小镇员工兼居民
- `Skills` 是工具屋中的能力
- `Workflow` 是镇中心任务板上的协作委托
- `Channels` 是邮局
- `Sessions / Logs` 是角色的今日行动记录
- `Workspace` 是仓库

产品定位：

- 首先是一个可玩的本地 AI 小镇
- 其次是一个多 Agent 可视化管理界面
- 同时具备轻养成属性，但不做重 RPG

一句话定义：

> 这是一个“活着的本地 AI 多 Agent 小镇”，而不是传统面板换一套皮肤。

## 2. 核心体验

用户可以：

- 进入本地 AI 小镇
- 看到 `OpenClaw` 作为老板角色在管理和指挥全镇
- 看到多个 Agent 自主生活、移动、工作、协作
- 点击 Agent 对话
- 给 Agent 安装技能
- 在任务板上发布或观察协作任务
- 查看角色最近工作内容和状态
- 通过日常互动获得轻养成体验

系统要让用户感知到：

- `OpenClaw` 是有存在感的管理者，而不是隐藏在后台的抽象进程
- Agent 平时会生活，不是静止图标
- Agent 工作时会回办公室，对着电脑敲键盘
- 安装技能后，角色会有新的能力和行为
- 多 Agent 之间可以共同完成任务

## 3. 风格定义

### 视觉风格

- 2D 俯视角
- 像素格子地图
- 温暖卡通小镇氛围
- 参考方向：`Stardew Valley` 的清爽像素乡镇感

### 页面气质

- 主画面以地图为中心，不是后台卡片堆叠
- UI 是轻 HUD 和轻抽屉，不喧宾夺主
- 避免玻璃拟态、科技蓝紫、强后台感
- 强调自然色和生活感：草地、木屋、石路、办公桌、邮局、仓库

### 推荐色彩

- 草地：低饱和绿色
- 木屋：暖棕色
- 办公室：浅木色 + 米白 + 少量蓝灰
- 邮局：红棕或橙色点缀
- 工具屋：深木色 + 金属灰
- 仓库：卡其 + 深棕

## 4. 页面结构

建议新增独立路由，例如：

- `/town`

`/town` 不替代现有管理页，而是作为游戏化入口。

### 页面布局

- 中央：小镇主地图
- 左上：时间、天气、今日活跃 Agent 数、当前任务数
- 右上：`OpenClaw` 管理卡片，显示当前管理状态和全局调度入口
- 左下：当前选中 Agent 的头像、名字、状态、心情、体力
- 上方中部：镇中心任务板入口
- 底部快捷栏：邮局、工具屋、仓库、Agent 名册
- 右侧抽屉：选中 Agent 后显示详情

### 右侧抽屉内容

- 当前状态
- 当前任务
- 今日行动记录
- 已安装技能
- 聊天面板
- 快捷操作

## 5. 地图方案

MVP 阶段不建议做太多副地图，先控制在 3 张以内。

### 地图 1：小镇主地图

用途：

- Agent 闲逛
- 用户选中并控制空闲 Agent 移动
- 进入建筑
- 观察任务入口
- 和角色发起对话

地图元素：

- 镇中心任务板
- `OpenClaw` 指挥台或镇长办公室入口
- 邮局
- 工具屋
- 仓库
- 办公楼入口
- 小路、树木、草地、长椅、路灯、装饰物

### 地图 2：共享办公室

用途：

- 工作中的 Agent 回到此处
- 在工位前敲键盘
- 展示协作中的多个 Agent
- 作为“工作可视化”核心空间

地图元素：

- `OpenClaw` 老板工位或总控桌
- 多个工位
- 电脑桌
- 白板或任务屏
- 状态指示灯

### 地图 3：设施交互层

MVP 不必做成完整可走动地图，可以先做成半屏场景或交互面板：

- 工具屋：技能管理和安装
- 邮局：通道状态和消息收发
- 仓库：工作区文件和产物

后续版本如效果好，再把它们独立为完整室内地图。

## 6. Agent 行为设计

## 6.1 基础规则

Agent 有两种控制方式：

- 自动生活
- 用户接管

默认是自动生活。

## 6.2 自动生活状态

### 空闲时

- 在小镇主地图闲逛
- 按随机路点巡游
- 偶尔驻足
- 偶尔和其他 Agent 短暂交流
- 偶尔走到建筑门口停留

### 工作时

- 收到任务后切换到工作状态
- 自动前往办公室入口
- 切换到办公室场景
- 找到自己的工位
- 播放敲键盘动画
- 任务完成后离开办公室并回到空闲状态

### 养成属性影响

角色可维护一些轻量属性：

- 心情
- 体力
- 专注度
- 技能熟练度
- 亲密度

这些属性影响展示和部分行为频率，但不让系统过度复杂。

## 6.3 用户接管状态

当用户选中 Agent 时：

- 可以查看详情
- 可以发起聊天
- 若 Agent 当前空闲，可使用方向键或 `WASD` 控制移动

建议规则：

- 只有空闲 Agent 可被完整接管移动
- 工作中的 Agent 默认不可被直接拖离工位
- 如果后续要支持打断任务，应显式提供“暂停任务并接管”按钮
- `ESC` 或一定时间无操作后退出接管状态

## 6.4 Agent 状态机

推荐最小状态集合：

- `idle`：空闲
- `wander`：闲逛
- `chatting`：短暂交流
- `moving_to_work`：前往工作
- `working`：工作中
- `returning`：工作完成返回
- `selected`：被用户选中
- `controlled`：被用户手动控制
- `paused`：任务暂停
- `error`：执行异常

状态切换触发源：

- `workflow run`
- `session activity`
- `log entry`
- 用户点击
- 用户接管
- 技能安装完成

## 7. 场景对象映射

### OpenClaw = 老板 / 镇长 / 管理者

- 是全镇的最高管理角色
- 负责分发任务、组织协作、查看全局状态
- 在视觉上必须是明确可见的角色或岗位，不是纯文字概念
- 点击 `OpenClaw` 后，打开全局管理视图

推荐表现：

- 小镇主地图有单独的 `OpenClaw` 指挥台或镇长办公室
- 办公室地图中有明显的老板工位
- 任务开始时，由 `OpenClaw` 发出委派提示
- 任务完成后，Agent 会向 `OpenClaw` 汇报或结算

### Agent = 小镇员工兼居民

- 地图上的主角色单位
- 有名字、头像、状态、属性、技能集
- 平时是生活中的居民，工作时是受管理的员工

### Skills = 工具屋

- 作为技能安装和查看的入口
- 安装技能后，角色解锁新能力或新行为

例如：

- 安装搜索技能后，工作动画出现资料检索动作
- 安装图像技能后，可解锁画板或创作台相关动作
- 安装提醒技能后，可触发邮局或公告栏互动

### Workflow = 镇中心任务板

- 展示当前任务
- 展示委托进度
- 展示参与 Agent
- 点击后查看任务详情

### Channels = 邮局

- 展示通道状态
- 作为消息输入输出的象征性建筑
- 未来可扩展邮件、消息通知、外部事件投递

### Sessions / Logs = 今日行动记录

- 点击 Agent 后查看
- 显示它今天做了什么
- 展示最近回复、技能调用、任务事件、异常信息

### Workspace = 仓库

- 展示工作产物
- 展示文件、报告、工作流输出
- 可作为任务产物存放地

## 8. 聊天和互动

点击 Agent 后可以：

- 对话
- 查看状态
- 查看当前任务
- 查看今天做过的事情
- 安排简单行为

建议聊天分两层：

- 地图上的气泡式简短回应
- 右侧抽屉里的正式聊天面板

这样既保留游戏感，也保证可读性。

## 9. 任务协作表现

不要只把协作显示成列表，需要在地图中可感知。

推荐表现：

- 任务板出现新委托时高亮提示
- `OpenClaw` 出现派单或指挥动作提示
- 指定 Agent 后，角色从小镇进入办公室
- 多个 Agent 在办公室不同工位同时工作
- 点击任务板或角色，可以看到当前协作进度
- 任务完成后，在仓库中出现产物，或在地图上弹出完成提示

## 10. 技术实现建议

## 10.1 推荐技术路线

- 站点框架：React
- 场景渲染：PixiJS
- 地图编辑：Tiled
- UI 面板：React + Tailwind
- 数据同步：现有 REST API + WebSocket
- 状态层：新增 `TownState`

## 10.2 为什么不用纯 DOM

纯 DOM + CSS 可以做原型，但不适合长期维护以下需求：

- 像素地图
- 多角色移动
- 分层渲染
- 角色朝向和动画
- 后续扩展更多建筑和场景

## 10.3 为什么优先 PixiJS 而不是 Phaser

本项目的重点不是完整游戏引擎能力，而是：

- 小镇地图显示
- 角色移动
- 简单动画
- 与 React 业务面板共存

`PixiJS` 更轻，更适合把“游戏场景”作为一个页面模块嵌入现有前端。

## 10.4 前端分层建议

建议分成 4 层：

### 1. 数据层

负责读取：

- agent 列表
- workflow
- skills
- sessions
- logs
- websocket 事件

### 2. 领域层

新增 `TownState`，把真实业务数据翻译成游戏状态：

- 哪些 Agent 空闲
- 哪些 Agent 正在工作
- 哪些 Agent 在办公室
- 哪些建筑需要高亮
- 哪些事件需要播报

### 3. 场景层

负责：

- 地图渲染
- 角色显示
- 移动
- 动画
- 建筑点击区域

### 4. UI 浮层

负责：

- HUD
- Agent 抽屉
- 聊天框
- 任务板
- 技能安装
- 日志与详情

## 11. 资源与素材建议

素材来源可参考：

- Kenney Assets
- itch.io Game Assets
- OpenGameArt

使用原则：

- 先选一个主素材风格做统一基底
- 严格统一 tile 尺寸
- 严格统一角色比例
- 严格统一阴影方向和色板
- 优先选择可修改、授权清晰的素材

建议：

- 地图和建筑素材以同一来源为主
- 角色素材可以单独挑，但必须风格接近
- UI 图标可以用像素风补充，不要混太多现代扁平图标

## 12. 页面美术方向

## 12.1 主地图体验

用户进入页面时，应该先看到：

- 一个有主角层级的小镇，`OpenClaw` 的位置和身份一眼可辨认
- 温暖像素小镇
- 正在活动的角色
- 明确可点的建筑
- 少量但清晰的状态 HUD

而不是：

- 大量面板
- 大量表格
- 大量设置项

## 12.2 构图原则

页面要先解决“好不好看”，再解决“功能有没有都放上去”。

建议构图：

- 画面中心是镇中心广场或主路口，作为第一视觉焦点
- `OpenClaw` 的指挥点要位于主视觉轴附近，不能藏在角落
- 邮局、工具屋、仓库分布在主地图四周，形成清晰路径关系
- 办公楼入口和主广场之间要有明显道路连接，保证“接任务 -> 去上班”的视觉逻辑顺畅
- 主要建筑之间保留呼吸空间，不要挤成一团

## 12.3 建筑辨识度

每个建筑必须通过轮廓、屋顶颜色和门口装饰一眼分辨。

建议：

- `OpenClaw` 指挥台：更醒目的屋顶、旗帜、招牌或控制屏元素
- 邮局：邮箱、红色标识、门口信件箱
- 工具屋：木箱、扳手、齿轮、工具架
- 仓库：堆叠箱子、推车、较厚重的建筑轮廓
- 办公楼：更规整的室内布局和工位感

不要让建筑只是换个名字的同款小房子。

## 12.4 UI 原则

- 地图优先，面板次之
- 只在需要时弹出右侧抽屉
- 底部快捷栏图标少而明确
- 使用像素边框和像素按钮风格
- 角色对话和状态采用气泡、徽章和简短文字
- 所有浮层都必须比地图更“轻”，不能压住主画面

## 12.5 视觉细节规范

为了保证页面真正好看，建议在第一版就固定以下细节：

- Tile 尺寸统一，推荐 `16x16` 基础像素格
- 显示缩放统一，推荐整数倍缩放，避免像素发糊
- 所有阴影方向统一，例如固定为右下阴影
- 角色描边粗细统一
- 屋顶、墙体、地面不要混用不同像素密度素材
- HUD 和弹窗使用米白、木色、深绿、深棕等自然配色
- 禁止在小镇页使用当前后台那种玻璃拟态卡片语言

## 12.6 动画原则

动画要少，但要值钱。

优先做这些：

- 角色 4 向行走
- 待机轻微呼吸或晃动
- 敲键盘循环
- 任务接取时的气泡或感叹号
- 邮局来信提示
- 任务完成时的轻量闪光

不建议第一版做这些：

- 大量粒子特效
- 花哨镜头缩放
- 复杂天气遮罩
- 过多无意义飘字

## 12.7 字体建议

- 标题、数字、徽章可用像素字体
- 正文和聊天内容继续用正常中文字体

原因：

- 像素字体适合装饰和游戏感
- 大段中文正文若全用像素字体，可读性会很差

## 12.8 不好看的常见原因

如果后面页面效果不好，通常不是因为功能少，而是因为以下问题：

- 地图主体不明确，用户一进来不知道看哪里
- `OpenClaw` 和 Agent 的层级关系不清晰
- 建筑风格混乱，像拼素材
- UI 面板太多，遮住地图
- 现代后台图标和像素素材混搭
- 一屏里信息太满，没有留白

因此页面设计优先级应该是：

1. 主视觉构图
2. 建筑与角色风格统一
3. 交互层级清晰
4. 再补功能入口

## 13. 数据映射建议

当前项目已有能力可以直接映射：

- `openclaw runtime / status` -> 老板角色与全局调度状态
- `agents` -> 小镇居民列表
- `skills` -> 工具屋技能库存
- `workflow runs` -> 当前协作任务
- `sessions` -> 角色个人工作上下文
- `events / logs` -> 今日行动记录
- `workspace files` -> 仓库产物
- `channels` -> 邮局状态

建议不要直接把原始接口结构塞进场景层，而是先转换成统一格式。

### 从当前项目吸收的经验

这个项目已经有一些很适合继承到 `/town` 模式里的成熟能力，不需要重做。

#### 1. 本地优先的产品形态是对的

当前项目采用：

- Go 后端
- 前端嵌入式部署
- SQLite 本地存储
- 单程序运行

这很适合 AI 小镇的目标，因为用户会把它当成一个本地常驻产品，而不是临时网页。

对小镇模式的启发：

- 保持本地优先
- 保持单程序启动
- 不要为了小镇模式拆成复杂微服务

#### 2. 事件流骨架值得直接复用

当前项目已经打通了：

- 外部事件进入系统
- 系统事件写入数据库
- WebSocket 实时广播
- 前端实时渲染

这对小镇模式非常关键，因为以下内容都依赖实时事件：

- Agent 状态变化
- `OpenClaw` 派单提示
- 任务开始和完成提示
- 角色聊天气泡
- 今日行动记录

结论：

- 小镇不应自己再造一套实时机制
- 应该直接复用现有事件流，再在上层转译成游戏表现

#### 3. 工作流模型已经足够支撑“任务板”

当前项目不是只有一个任务列表，而是已经具备：

- 模板
- 运行实例
- 步骤
- 事件
- 控制操作

这意味着小镇中的“镇中心任务板”不是纯展示，而是可以直接映射真实运行状态。

对小镇模式的启发：

- 任务板直接绑定 workflow runs
- 协作中的 Agent 直接绑定 workflow 参与者和步骤状态
- 办公室工作动画由 workflow 状态驱动

#### 4. 多 Agent 管理抽象已经成型

当前项目已有：

- 默认 Agent
- 多 Agent 列表
- bindings 路由
- Agent 身份
- Agent 核心文件
- Agent 会话统计

这些能力说明，小镇居民系统不需要从零发明。

对小镇模式的启发：

- 小镇居民直接来自现有 Agent 列表
- 每个 Agent 都应保留自己的身份、会话和工作历史
- `OpenClaw` 老板角色应站在这些 Agent 之上做全局管理

#### 5. `skills / plugins / workspace` 的业务概念已经天然可游戏化

这三个模块与小镇建筑的映射非常自然：

- `skills` -> 工具屋
- `plugins / channels` -> 邮局和外部联络设施
- `workspace` -> 仓库

对小镇模式的启发：

- 优先复用现有业务语义
- 不要重新创造一套和现有系统割裂的新名词体系

#### 6. 状态聚合接口值得继承

当前项目已经有统一状态总览，包括：

- OpenClaw 运行状态
- gateway 状态
- 通道启用情况
- 当前模型
- 进程状态

这非常适合做 `OpenClaw` 老板角色的总控视角。

对小镇模式的启发：

- 右上角老板管理卡片可以直接基于状态总览构建
- 不必在小镇页里重新发很多零散请求

#### 7. mock 和 demo 能力应该直接用于小镇原型

当前项目已经有：

- mock API
- demo 日志
- demo skills
- demo agents

这意味着 `/town` 第一版完全可以先用 mock 数据跑通。

对小镇模式的启发：

- 先做可试玩原型
- 再接真实数据
- 不要第一天就把真实后端耦合进所有场景逻辑

#### 8. 当前项目最不该继承的是后台视觉风格

虽然系统能力值得继承，但当前页面审美不适合小镇模式。

不建议继承：

- 玻璃拟态卡片
- 传统控制台式布局
- 过强的后台表单感
- 现代图标和像素地图混搭

结论：

- 继承系统能力
- 重做小镇页面视觉
- 保持“底层真实，表层游戏化”

#### 9. 代码结构上要避免继续把逻辑直接堆进页面或 handler

当前项目已经有不少业务逻辑聚合在 handler 和页面里。

小镇模式如果继续照搬，很快会变乱。

建议：

- API 层继续复用
- 新增 `TownState`
- 用 `TownState` 负责把真实业务状态翻译成地图状态、角色状态和建筑提示
- 场景层只负责渲染和交互

## 14. MVP 范围

MVP 只验证“AI 小镇能不能成立”，不追求全部功能完整。

### 必做

- 新增 `/town` 页面
- 小镇主地图
- 办公室地图
- `OpenClaw` 老板角色或指挥台
- 3 个可见 Agent
- Agent 空闲时闲逛
- Agent 工作时回办公室敲键盘
- 点击 Agent 查看详情
- 空闲 Agent 支持方向键移动
- 镇中心任务板
- 工具屋技能查看与安装入口
- 右侧显示今日行动记录
- 使用 mock 数据先跑通一版

### 可延后

- 完整室内副地图
- 天气系统
- 装饰系统
- 更复杂的亲密度和成长数值
- 更复杂的寻路和碰撞
- 更多生活类小游戏

## 15. 开发阶段建议

## Phase 1：可试玩原型

目标：

- 先把视觉和交互骨架跑通

内容：

- `/town` 路由
- 主地图静态背景
- 角色显示
- 选中角色
- 方向键移动
- 右侧 Agent 抽屉
- mock 任务与 mock 行动记录

## Phase 2：真实数据接入

目标：

- 让小镇开始反映真实 OpenClaw 状态

内容：

- 接入 agents
- 接入 workflows
- 接入 logs / sessions
- 用 websocket 驱动状态变化
- 工作状态进入办公室

## Phase 3：轻养成闭环

目标：

- 提升留存和趣味性

内容：

- 心情/体力
- 技能熟练度
- 日常互动奖励
- 角色偏好和简单个性

## Phase 4：扩展玩法

目标：

- 让小镇更像一个长期可玩产品

内容：

- 完整室内地图
- 更多建筑
- 家具与装饰
- 特殊事件
- 节日任务

## 16. 风险与控制

主要风险：

- 美术资源风格不统一
- 地图越做越多导致范围失控
- 过度游戏化导致真实管理效率下降
- 多 Agent 同屏活动后信息杂乱
- 全靠 LLM 决策导致行为不可控

控制策略：

- 先做 3 张地图以内
- 先做规则驱动的生活模拟
- 保留右侧详情和底部快捷入口
- 游戏表现和真实数据分层
- 先 mock，再接真实接口

## 17. 当前结论

这个方向值得做，但必须按“游戏化管理模式”而不是“完整 RPG”推进。

第一阶段的正确目标不是：

- 做一个内容很多但很重的游戏

而是：

- 做一个进入后就能让用户感受到“`OpenClaw` 正在管理一群 AI 员工，而这些 AI 在小镇里真实生活和工作”的页面

下一步落地建议：

1. 先创建 `/town` 页面和基础布局
2. 先做主地图 + 办公室 2 张场景
3. 先用 mock 数据驱动 3 个 Agent
4. 跑通“闲逛 -> 接任务 -> 回办公室工作 -> 完成任务”的完整链路
5. 再逐步接入真实 OpenClaw 数据

## 18. 智能体编辑页优化方案

### 18.1 背景

当前「编辑智能体」弹窗已经承载了大量能力，但整体体验存在明显问题：

- 用户无法快速理解“这个智能体是干什么的”
- `skills`、`tools`、协作能力等重要信息不够直观
- 页面上大量中英混排，对非技术用户阅读成本很高
- 结构化配置与高级 JSON 混在一起，容易让用户失去信心
- 信息顺序更像“底层配置面板”，不像“业务角色配置页”

这会导致两个后果：

- 用户看得到很多字段，但不知道该改什么
- 真正重要的能力已经存在，却没有被感知到

### 18.2 改版目标

新的智能体编辑页要先回答 5 个核心问题：

1. 这个智能体负责什么工作
2. 它会使用哪些技能
3. 它能调用哪些工具
4. 它的权限有多大
5. 它会在什么情况下接管消息

设计目标：

- 先讲业务职责，再讲技术配置
- 默认展示 80% 用户最常改的能力
- 技能、工具、权限必须可见且可理解
- 文案中文优先，英文只保留为技术辅助信息
- 高级 JSON 不再主导主流程

### 18.3 当前问题诊断

#### 1. 信息架构错误

当前页面先展示的是：

- `ID`
- `workspace`
- `agentDir`
- `model`
- `sandbox`

但用户更在意的是：

- 它是谁
- 它负责什么
- 它能做什么

这说明页面是按实现结构组织的，而不是按用户心智组织的。

#### 2. 技能能力不可见

当前 `skills` 更像“侧面快照”而不是“编辑页主能力”。

结果是：

- 实际已经支持技能体系
- 用户却会觉得“这里没有技能配置”

#### 3. 工具能力被拆散

`tools.profile`、`allow/deny`、`agentToAgent`、`session visibility`、`sandbox` 分散在多个分区。

结果是：

- 用户不能形成“这个智能体到底有什么能力”的整体认知
- 高权限与高风险项不够显眼

#### 4. 文案太技术化

大量文案是：

- 中文 + 英文并列
- 技术键名直接暴露
- 长说明文字堆叠

结果是：

- 看起来很专业，但不易理解
- 用户知道字段存在，但不知道如何做决策

#### 5. 高级模式过早进入主流程

当前页面一直在提醒用户：

- “更复杂请去 Advanced”
- “高级字段请继续编辑 JSON”

这会放大复杂感，让主流程失焦。

### 18.4 新的信息架构

编辑弹窗改为「左侧导航 + 主编辑区 + 右侧摘要栏」。

#### 左侧导航改为 6 个中文分区

1. 基本信息
2. 角色与模型
3. 技能与工具
4. 权限与执行环境
5. 路由与协作
6. 高级设置

#### 主编辑区遵循“先业务，后技术”

第一屏必须先出现：

- 智能体名称
- 角色定位
- 职责说明
- 主要工作内容

只有在用户理解了“它是谁、干什么”之后，才继续往下配置模型、工具、权限。

#### 右侧摘要栏展示当前生效结果

固定展示：

- 当前职责摘要
- 当前主模型
- 生效技能数
- 工具权限等级
- 默认接管状态
- 风险提示

这个摘要栏的目标不是编辑，而是帮助用户确认“我现在到底配成了什么样”。

### 18.5 分区设计

#### A. 基本信息

放在最前面，字段顺序调整为：

1. 智能体名称
2. 职责说明
3. 适合处理的任务类型
4. 是否默认接管
5. 标识 ID
6. 工作目录
7. 智能体配置目录

说明：

- “职责说明”应该成为第一优先级字段
- `ID` 不应该再是第一输入项
- `workspace` 对外显示为“工作目录”
- `agentDir` 对外显示为“智能体配置目录”

#### B. 角色与模型

将当前的 `behavior + identity + context` 合并。

包含：

- 角色模板
- 主模型
- 备用模型
- 温度
- 最大输出
- 上下文预算
- 身份名称
- 对外风格
- 头像

建议新增“角色模板”：

- 编码助手
- 运营助手
- 路由助手
- 客服助手
- 分析助手

作用：

- 帮用户先建立角色认知
- 再去微调模型参数

#### C. 技能与工具

这是本次改版最关键的增强区。

必须显式展示：

- 当前生效技能
- 技能来源
- 当前工具能力

建议分为两块：

1. 生效技能
   - 显示技能名称、来源、是否启用
   - 支持“前往技能中心管理”
   - 如果当前智能体通过 `workspace` 间接继承了技能，也要展示“当前生效”

2. 工具能力
   - 用能力卡片展示，而不是只显示 JSON
   - 卡片建议包括：
     - 文件读写
     - 命令执行
     - 网络访问
     - 浏览器
     - 消息发送
     - 委派给其他智能体

每张卡片只展示三种状态：

- 跟随全局
- 已启用
- 已关闭

`tools.allow / tools.deny` 放入“高级工具规则”折叠区，不作为第一视觉层。

#### D. 权限与执行环境

把现在 `Access & Safety` 改成更能理解的中文结构。

第一层只保留 4 个预设：

- 跟随全局
- 只读执行
- 工作区可写
- 高权限执行

高级展开后才显示：

- sandbox 模式
- workspace 挂载方式
- docker 网络
- docker 初始化命令
- bind 挂载

这样可以先让用户理解“权限等级”，再深入到底层参数。

#### E. 路由与协作

这个分区回答两个问题：

- 什么时候会分配给它
- 它能不能和别的智能体协作

应包含：

- 是否默认接管
- 当前命中它的路由规则摘要
- Agent 间委派
- 会话可见范围
- 可调用的子智能体

这里不应只展示字段，而要展示“实际意义”：

- 当前没有显式规则，将通过默认回落接管
- 当前仅允许委派给 `reviewer`、`writer`
- 当前只能看本智能体自己的会话

#### F. 高级设置

只留给高级用户。

包含：

- model JSON
- tools JSON
- sandbox JSON
- identity JSON
- params JSON
- runtime JSON

原则：

- 默认折叠
- 放到最后
- 清楚提示哪些结构化字段会覆盖它

### 18.6 文案规范

#### 中文优先

页面主标题、标签、按钮统一使用中文。

例如：

- `基础信息 (Basic)` -> `基本信息`
- `Behavior` -> `角色与模型`
- `Access & Safety` -> `权限与执行环境`
- `Collaboration` -> `路由与协作`
- `Advanced` -> `高级设置`

#### 英文只作为辅助

英文只出现在两种场景：

- 技术键名说明，例如 `tools.allow`
- tooltip 或帮助文本中的补充说明

不再使用“中文 + 英文并列”作为主文案。

#### 帮助文案改短

原则：

- 每段说明不超过 2 行
- 默认只讲“为什么需要这个配置”
- 技术细节收进“查看更多说明”

### 18.7 关键交互优化

#### 1. 默认焦点改为“职责说明”

打开编辑页后，不应先聚焦 `ID`，而应聚焦职责相关区域。

#### 2. 摘要栏实时反馈

用户改动后，右侧摘要栏要实时刷新：

- 当前模型
- 工具能力等级
- 默认接管状态
- 当前技能数量

#### 3. 风险提示可视化

如果启用了高风险能力，应直接提示：

- 已允许命令执行
- 已开放网络访问
- 已关闭沙箱

#### 4. 保存前差异摘要

点击保存前，可在底部显示：

- 本次修改了：角色与模型、工具能力、协作范围

让用户知道自己改了什么。

### 18.8 分阶段落地

#### Phase 1：界面重构，不改后端协议

目标：

- 快速提升可理解性

内容：

- 重命名分区
- 中文化主文案
- 调整字段顺序
- 在编辑页展示当前生效技能
- 将工具能力改成能力卡片展示
- 将高级 JSON 收拢到最后

#### Phase 2：增强结构化能力

目标：

- 降低“必须会写 JSON”的门槛

内容：

- 新增职责说明字段
- 新增角色模板
- 将常见工具开关做成结构化项
- 将权限档位做成预设

#### Phase 3：保存与诊断增强

目标：

- 让复杂配置更可控

内容：

- 保存前差异预览
- 风险扫描
- 显示继承来源
- 显示实际生效值

### 18.9 验收标准

改版完成后，至少满足以下标准：

- 用户在 10 秒内能看懂这个智能体“负责什么”
- 用户在 15 秒内能找到“技能”和“工具能力”
- 用户不需要看 JSON，也能完成常见编辑
- 页面主文案不再出现大面积中英混排
- 高风险权限在保存前能被明确看见

### 18.10 当前建议

如果按投入产出比排序，最值得先做的是：

1. 重构分区名称与顺序
2. 增加“职责说明”与“角色模板”
3. 在编辑页显式展示生效技能
4. 把工具权限改成能力卡片
5. 将高级 JSON 明确降级为最后一层

这五项做好后，编辑智能体页面才会从“底层配置面板”变成“用户真正能用的角色配置页”。

## 19. AI 小镇 V2：OpenClaw 协作观测皮肤定稿

### 19.1 重新定位

`AI 小镇` 不再按“独立可玩小游戏”定义，而是按 `OpenClaw` 的网页可视化皮肤定义。

核心目标只有一个：

- 让用户在网页里观察 `OpenClaw` 和子 Agent 正在做什么

因此，页面的本质不是“玩地图”，而是：

- 选 Agent
- 进入办公室
- 由 `OpenClaw` 发起任务或调度子 Agent
- 观察 session / spawn 协作过程

页面职责拆分为：

- `智能体` 页面：创建、配置、管理 Agent
- `AI 小镇` 页面：选择 Agent、发起任务、观察执行现场

### 19.2 核心原则

#### 1. OpenClaw 永远是主控

- 每个任务都由 `OpenClaw` 发起、接管或调度
- Agent 不是独立主角，而是被 `OpenClaw` 组织起来的协作成员

#### 2. 页面必须映射真实协作模型

- 页面状态要尽量对应真实的 `session`、`sessions.spawn`、日志和调度结果
- 不能只做“看起来像在忙”的假动画层

#### 3. 地图只是观测容器

- 保留像素小镇地图
- 但地图不再承担复杂玩法，不强调走动控制
- 地图和办公室都只是协作状态的可视化壳

#### 4. 优先做观测，而不是做游戏机制

- 优先级是“用户看懂 AI 在干嘛”
- 不是“用户能在小镇里做多少操作”

### 19.3 新的产品目标

新版 `AI 小镇` 要帮助用户完成以下事情：

1. 快速看到当前有哪些 Agent 可参与协作
2. 快速选择最多 10 个 Agent，作为办公室待命成员
3. 在办公室内给 `OpenClaw` 发出任务指令
4. 观察 `OpenClaw` 是否单独执行，或是否派生子 Agent 协作
5. 观察任务执行过程、日志、当前忙碌成员和办公室成员变化
6. 在 IM 自动触发任务时，看到 `OpenClaw` 如何把 Agent 拉进办公室工作

### 19.4 非目标

新版 `AI 小镇` 不再承载以下目标：

- 不再作为 Agent 的配置控制台
- 不再强调手动移动、接管玩法
- 不再保留与协作无关的“小游戏式”建筑功能
- 不再堆放大量后台卡片或占位模块
- 不再追求完整模拟经营或轻养成

### 19.5 页面信息架构

新版只保留两个核心场景：

1. 主镇
2. 办公室

#### 主镇

主镇是“准备区”和“入口页”。

作用：

- 展示小镇像素视觉
- 展示少量可见 Agent
- 让用户选择要带进办公室的 Agent
- 展示当前已选 Agent 与技能覆盖

主镇不再负责：

- 输入任务
- 查看长日志
- 展示仓库、邮局等弱相关入口

#### 办公室

办公室是“执行现场”和“观察区”。

作用：

- 展示 `OpenClaw`
- 展示办公室待命 Agent
- 展示正在忙碌的 Agent
- 输入任务并由 `OpenClaw` 开始执行
- 查看任务日志与 session / spawn 关系

### 19.6 主镇设计规则

#### 1. 地图中显示的角色数量受限

主镇地图中可见角色总数控制在 `6` 个以内。

可见角色来源：

- 常用展示 Agent
- 少量空闲装饰角色

#### 2. 主镇展示 Agent 的选择规则

主镇可见 Agent 采用：

- 完全随机显示
- 但对最近使用过的 Agent 提高权重

目标是：

- 保持地图有变化
- 同时让常用 Agent 更容易被看见

#### 3. 已选 Agent 不显示在主镇

一旦 Agent 被选中并进入办公室：

- 它不再显示在主镇地图
- 它改为显示在办公室场景

#### 4. 主镇右侧信息区只保留 3 类内容

- 已选 Agent
- 技能汇总
- `去办公室` 按钮

主镇不再显示：

- 心情
- 体力
- 聊天占位
- 任务输入框
- 邮局 / 仓库 / 多余演示卡

#### 5. 主镇使用右侧抽屉完成选人

主镇增加 `Agent 列表` 按钮。

点击后打开右侧抽屉，抽屉中：

- 支持搜索
- 展示完整 Agent 列表
- 每个 Agent 显示：
  - 名称
  - 职责摘要
  - skills 列表
  - 选中 / 未选中状态
- 最多选中 `10` 个 Agent

### 19.7 办公室设计规则

#### 1. 办公室是执行态主场景

办公室中固定存在：

- `OpenClaw`
- 已选中的办公室成员
- 被 IM 自动拉入的临时成员

#### 2. 办公室内输入任务

任务输入框只出现在办公室内。

用户在办公室输入任务并点击开始后，含义是：

- 由 `OpenClaw` 正式发起主任务 session

#### 3. 办公室成员不随任务自动离开

任务完成后：

- Agent 不自动回主镇
- 而是继续留在办公室待命、闲逛或停留

只有以下情况才会回主镇：

- 用户把它设为非选中
- `OpenClaw` 将其移出办公室成员池

#### 4. 办公室提供日志弹窗

办公室保留一个 `任务日志` 按钮。

点击后弹窗展示：

- 当前任务日志
- 主任务 session
- 子 Agent session
- 当前状态和完成情况

日志不常驻主界面，避免页面再次堆叠。

### 19.8 OpenClaw 协作模型映射

新版 `AI 小镇` 必须明确体现 `OpenClaw` 与子 Agent 的真实关系。

#### 1. 主任务 session

- 每次任务由 `OpenClaw` 发起主任务 session
- 如果 `OpenClaw` 本身支持并行，则页面也支持多个主任务同时存在

#### 2. 子任务 session

- 当 `OpenClaw` 需要其他 Agent 协作时，再通过 `sessions.spawn` 等机制派生子任务 session
- 页面上应明确区分：
  - 哪些 Agent 只是办公室待命
  - 哪些 Agent 当前有活跃子 session

#### 3. 办公室成员池与活跃执行分离

页面不要把“在办公室”与“正在工作”混为一谈。

应拆成两层：

- 成员层：是否在办公室待命
- 执行层：是否有活跃 session 正在运行

### 19.9 推荐状态模型

为了更贴近真实运行状态，建议把 Agent 状态拆成多个维度，而不是只保留一个字符串状态。

#### 1. 空间位置

- `town`
- `office`

#### 2. 办公室成员关系

- `unselected`
- `selected`
- `auto_added`

说明：

- `selected` 表示用户手动选中并带进办公室
- `auto_added` 表示 IM 或 `OpenClaw` 调度时自动拉入办公室

#### 3. 执行状态

- `idle`
- `standby`
- `busy`
- `completed`
- `error`

#### 4. session 关联状态

- 无活跃 session
- 参与主任务 session
- 参与子任务 session

### 19.10 手动流程

手动流程定义为：

1. 用户在主镇通过抽屉选中 Agent
2. 点击 `去办公室`
3. 已选 Agent 从主镇移入办公室
4. 用户在办公室输入任务
5. `OpenClaw` 创建主任务 session
6. 如有需要，`OpenClaw` 继续 `spawn` 子 Agent session
7. 用户通过办公室场景和日志弹窗观察执行过程

特殊规则：

- 即使一个 Agent 都不选，也允许 `OpenClaw` 单独进入办公室执行

### 19.11 IM 自动触发流程

IM 自动触发流程定义为：

1. 用户通过 IM 向 `OpenClaw` 发送消息
2. `OpenClaw` 自动判断是否需要子 Agent
3. 如有需要，自动把相关 Agent 拉入办公室
4. 自动创建或续接主任务 session，并视需要 `spawn` 子 session
5. 网页仅提示：
   - `OpenClaw 正在办公室执行任务`
6. 页面不强制切换到办公室
7. 用户自行决定是否进入办公室观察

补充规则：

- IM 自动拉入的 Agent 在任务完成后，也自动留在办公室待命

### 19.12 UI 精简规则

以下内容从新版 `AI 小镇` 中移除：

- 邮局
- 仓库
- 主镇任务板
- 心情 / 体力
- 手动移动十字键
- 与协作观测无关的演示卡片
- 与后台面板重复的复杂配置入口

以下内容保留，但语义要调整：

- 小镇地图：保留为主镇视觉壳
- 办公室：保留为执行现场
- Agent：保留为可见角色和办公室成员
- OpenClaw：保留为核心调度者

### 19.13 页面成功标准

如果新版方向正确，用户打开 `AI 小镇` 后应在很短时间内理解以下几点：

1. `OpenClaw` 是协作中心
2. 主镇是选人和进入办公室的入口
3. 办公室是执行现场
4. Agent 在办公室不等于一定正在工作
5. 真正的工作状态由 session / spawn 驱动
6. 页面是在“观察 AI 协作”，而不是在“玩一个小游戏”

### 19.14 下一步实施建议

建议后续实施按如下顺序推进：

1. 先调整页面定位与信息架构
2. 再重构状态模型，使其支持办公室成员池和活跃 session 分离
3. 再接入 `OpenClaw`、`session`、`sessions.spawn`、日志等真实协作数据
4. 最后补足像素视觉、办公室表现和状态动画
